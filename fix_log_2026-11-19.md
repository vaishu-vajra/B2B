Changed the FastAPI fallback to `gpt-6.2-sol` and set the persistent Windows user environment variable `OPENAI_MODEL` to `gpt-6.2-sol`. The environment override remains supported. Restart FastAPI; start it from a new PowerShell window to inherit the persistent user setting. Confirm the model in request logs.

## Fix 4 — Reuse stable prompt context and record cache usage (19 November 2026)

### What was there
- The API built one prompt string containing fixed instructions, the selected-stage instruction, all mapped project files, and changing run data.
- It did not separate the reusable project context from the period brief and selected prior outputs.
- The API response usage was not recorded for cache comparisons.

### What is the problem
When run-specific material changes, the one-message prompt does not clearly mark the end of the reusable prefix. Repeat calls may therefore miss cache reuse or cache-write changing run data. Without per-call cache and token metrics, reuse and input-cost impact cannot be compared.

### What is the fix
- Split the Responses API input into stable instructions, a stable mapped-source block, and a changing run-input block. The period brief, prior outputs, and run-specific fields come after the stable block; stable project knowledge follows a fixed order.
- Mark the reusable block as an explicit 30-minute cache breakpoint and use a stable stage-specific cache key for accounting. The run-specific suffix is excluded from the explicit cache write.
- Added an append-only JSONL usage log, recorded only when the API is used. Each row includes stage, model, response ID/status, stable-prefix fingerprint, input/output tokens, cached tokens, cache-write tokens by retention, and estimated input cost. It does not store prompt contents.
- The input-cost estimate uses the published Standard global GPT-6.2 Sol rates checked on 19 November 2026. It is an estimate from actual token counts, not the billing dashboard dollar amount. Other models without a configured rate are logged with a blank estimate.
- No skill was run and no OpenAI API call or key was used for this change.

### Where is the fix
- Prompt structure, cache settings, and usage logging: D:\SOCIAL CONTENT DELIVERY\api_pipeline\main.py
- Usage log will be created on the first normal API call at D:\SOCIAL CONTENT DELIVERY\api_pipeline\usage_logs\api_calls.jsonl; no log file was fabricated now.

## Fix 5 — Resume safely after a stage failure (19 November 2026)

### What was there
- The API runs one Context Assembler request for the selected receiving stage; it does not run a chain of workflow skills.
- SDK retries were disabled with max_retries=0. Every API status error stopped immediately, and all 429 errors received one general message.
- The stage input map already loads earlier outputs only from exact paths supplied for the selected stage.

### What is the problem
Temporary rate-limit or server-overload responses had no bounded retry, while a depleted credit balance was not identified distinctly. The full workflow cannot automatically resume across stages because this API does not orchestrate multiple stages.

### What is the fix
- Added one application-level retry for explicitly identified transient 429 rate-limit errors and 503 server-overload errors. It respects Retry-After; without that header it waits one second. If the requested wait exceeds 10 seconds, it stops and tells the user how long to wait.
- Kept SDK-level retries disabled, so the total retry count remains controlled. Timeouts and connection failures are not retried because the request may already have used credits or completed remotely.
- Detects credit_balance_exhausted and other billing/usage-limit codes and stops immediately with a specific message. These errors are never retried.
- Kept the API’s one-stage-at-a-time behavior. A failed Context Assembler call cannot trigger earlier skill runs because this endpoint does not run them. The stage map continues to require exact prior-output paths. Automated multi-stage resume would require a workflow runner and is outside this change.
- No skill was run and no OpenAI API call or key was used for this change.

### Where is the fix
- Bounded retry and billing-error handling: D:\SOCIAL CONTENT DELIVERY\api_pipeline\main.py
- Existing exact prior-output map: D:\SOCIAL CONTENT DELIVERY\api_pipeline\workflow_inputs.json
- Change record: D:\SOCIAL CONTENT DELIVERY\fix_log_2026-11-19.md

## K4.3 Interpretation rules

Use impressions and Published dates for review. Link posts to topics/formats only via reliable ID or exact copy; otherwise report breakdowns as unavailable. Compare like-for-like only when fields exist. Separate organic/paid, keep platform definitions, never infer lead attribution from engagement, never call a post a top performer without a defined comparison set. A historical claim reused in a new post is a supplied final claim: keep its scope, don't generalise, route concerns to human final-copy approval.

### K5.1 Vajra Global's feedback register

When a reviewer submits feedback in the application, save one row in learning_feedback.csv with the following fields. Use the same Feedback ID when recording a correction or resolving the feedback.
Field	How it is recorded
Feedback ID	Application-generated unique ID, e.g. VG-FB-001
Post ID	LinkedIn post or draft reference from the review
Draft version	Version under review, e.g. V1, V2 or V3
Review date	Date feedback was submitted
Reviewer	Name of the signed-in reviewer
Decision	Approved, rejected, rework required or clarification required
Feedback category	Voice, clarity, accuracy, relevance, strategy, CTA, visual or compliance
Original feedback	Exact reviewer comment
Required correction	What the reviewer asks the team to change
Final correction	What the team changed, recorded when available
Resolution	Accepted, pending or escalated
Recurring pattern	Yes or No, recorded when assessed
Rule impact	One-time preference, recurring preference or formal brand rule, recorded when assessed
Knowledge update required	Yes or No, recorded when assessed
Approved by	Person authorising a permanent rule change, recorded when applicable


Set Resolution to Pending when follow-up is still required. Leave unavailable fields empty until they can be recorded.
